# Monkey App — мобильный и десктопный клиент

Flutter-клиент к тому же бэкенду, что обслуживает сайт
([`../backend`](../backend)). Работает на Android, Windows и в вебе из одного кода.

## Зачем он, если есть сайт

Сайт ходит на сервер за каждым действием, поэтому заметен лаг: сеть + пробуждение
Render + запрос в Neon. Приложение построено по принципу **local-first** — данные
лежат копией на устройстве, интерфейс работает с ней мгновенно, а сервер
догоняется в фоне.

## Как устроена синхронизация

Источник правды один — PostgreSQL на сервере. Локальная копия это кэш, который
сходится с сервером сам.

```
        Приложение                        Сайт
            │                               │
   1. читает локальный кэш            каждый клик
      (мгновенно, без сети)           ждёт ответа
            │                               │
   2. пишет локально + в очередь            │
            │                               │
   3. фоном отправляет ──────► FastAPI ◄─────┘
                                  │
                             PostgreSQL (Neon)
```

Три правила, из которых берётся скорость:

1. **Чтение всегда из кэша.** `LocalStore` синхронный, экран рисуется до того,
   как уйдёт хоть один запрос.
2. **В сеть — только если кэш устарел.** Порог задаётся `Config.syncInterval`
   (сейчас 30 минут). Свежие данные не перезапрашиваются.
3. **Запись сначала локальная.** Список меняется сразу, запрос уходит следом.
   Нет сети — операция ложится в `SyncQueue` и уедет позже, ничего не теряется.

Синхронизация запускается при старте, при возврате из фона и по «потянуть вниз».

## Структура

| Файл | Отвечает за |
|---|---|
| `lib/core/config.dart` | адрес бэкенда, интервал синхронизации |
| `lib/core/local_store.dart` | локальное хранилище + отметки времени |
| `lib/core/sync_queue.dart` | очередь неотправленных изменений |
| `lib/core/api_client.dart` | HTTP к FastAPI, подстановка `user_id` |
| `lib/core/session.dart` | текущий пользователь |
| `lib/data/local_first_repository.dart` | общая механика local-first |
| `lib/data/*_repository.dart` | по одному на раздел, поверх общей механики |
| `lib/models/` | разбор ответов бэкенда |
| `lib/screens/` | экраны, `app_shell.dart` — навигация |
| `lib/theme.dart` | палитра, совпадающая с `frontend/style.css` |

Новый раздел добавляется тремя файлами: модель в `lib/models/`, репозиторий
поверх `LocalFirstRepository` и экран. Кэш, свежесть, очередь и откат при
ошибке достаются из базового класса.

### Записи, id которых генерирует сервер

Задача, заметка или трата появляются на экране мгновенно — с временным
отрицательным id (`LocalFirstRepository.nextTempId`). Настоящий приходит в
ответе на POST и подменяет временный. Если сети нет, запись живёт с временным
id до следующей синхронизации, а операции над ней в сеть не отправляются —
отправлять их некуда, пока сервер не знает о записи.

`LocalStore` намеренно с узким интерфейсом — под ним сейчас `shared_preferences`,
позже без правок в остальном коде можно подставить SQLite, когда данных станет
много и понадобятся запросы.

## Запуск

```bash
flutter run -d edge      # веб, ничего доустанавливать не нужно
flutter run -d windows   # нужен Visual Studio с «Разработка на C++»
flutter run -d android   # нужен Android Studio / Android SDK
```

Другой бэкенд (например, локальный) подставляется без правки кода:

```bash
flutter run -d edge --dart-define=API_BASE_URL=http://localhost:8000
```

## Разделы

| Раздел | Что умеет |
|---|---|
| Кино | просмотренное, к просмотру, фильмы/сериалы, поиск, оценки |
| Книги | прочитано, хочу прочесть, поиск, оценки |
| Задачи | день за днём, разовые и повторяющиеся, свайп для удаления |
| Тетрадь | цветные заметки и списки дел с пунктами |
| Цели | на месяц и на год, с полосой выполнения |
| Бюджет | траты по месяцам, категории с планом и перерасходом |
| Желания | свой виш-лист, друзья, брони и складчина на подарки |

Не перенесены **игры** (дурак, шахматы, бильярд, уно, 101). Они построены на
WebSocket и реальном времени: local-first им ничего не даёт, а объём работы
там больше, чем во всех остальных разделах вместе. На сайте они работают.

Также не переносились разделы, завязанные на разовые серверные операции:
разбор PDF-выписки в бюджете, AI-подборки и поездки.
